# CafePOS API reference

This is the reference for the HTTP and WebSocket API of the CafePOS backend.
It describes the code as it stands at commit `55cbd79` (2026-10-30), and it was written from the controllers, DTOs, services and gateways in `src/`.
Every route's roles were also checked against `test/authz-matrix.e2e-spec.ts`, which is the executable form of the permission matrix.

[`DESIGN.md`](../DESIGN.md) is the design specification and explains why the API is shaped the way it is.
When this file and `DESIGN.md` disagree, this file describes what the code does, and [section 9](#9-differences-from-designmd-and-known-rough-edges) lists the differences.
The [README](../README.md) endpoint table stops at Phase 3, and `postman/cafepos.postman_collection.json` has no request for the board, the KDS snapshot, payments, refunds, reports or the webhook.
This file is therefore the one place all 43 API routes are written down together.

## 1. Basics

### 1.1 Where things live

| Surface | Address | Notes |
|---|---|---|
| REST API | `http://<host>:3000/api/v1/...` | The port is `PORT` (default 3000). The version is in the URI. |
| Liveness and readiness | `/healthz`, `/readyz` | At the root, outside `/api/v1`, so orchestrator probes never move with an API version. |
| Metrics | `http://<host>:9464/metrics` | A separate listener on `METRICS_PORT`. No authentication, and the load balancer never routes it. |
| Realtime | `ws://<host>:3000/socket.io` | Socket.IO on its default path, with the namespaces `/kds`, `/kiosk` and `/board`. |

Every path in sections 6.1 to 6.12 is relative to `/api/v1`.
`/healthz`, `/readyz` and `/metrics` in section 6.13 are not.

### 1.2 Conventions

- Requests and responses are JSON (`Content-Type: application/json`).
  The two exceptions are the Stripe webhook (raw body, authenticated by signature) and the item image upload (`multipart/form-data`).
- Send a JSON object on every route that takes a body, even when every field is optional.
  A request with no body at all reaches the validator as `undefined` (Express 5 does not default `req.body` to `{}`), and fails with 422 (`field: "(root)"`, `rule: "invalid_type"`).
  For `POST /orders/:id/cancel`, where every field is optional, send `{}`.
- Routes without a body schema (`POST /orders/:id/checkout`, `POST /devices/:id/revoke`) ignore any body.
- Property names are camelCase.
- Money is an integer in minor units plus a `currency`, which is a three-letter ISO 4217 code taken from the `CURRENCY` setting (default `THB`).
  `"totalMinor": 12000` with `"currency": "THB"` is ฿120.00.
  The only fractional money-like value is `avgTicketMinor` in the sales report, which is a rounded statistic.
- Timestamps in responses are ISO-8601 UTC strings, for example `2026-06-11T07:42:10.000Z`.
  Timestamps you send must be UTC with a trailing `Z`.
  Offsets such as `+07:00` are rejected.
- A business day is a `YYYY-MM-DD` string (see [4.7](#47-business-day-and-queue-numbers)).
- Identifiers are UUIDs, generated by the server as UUIDv7.
  Every path parameter and every id in a body is validated as a UUID, and anything else is a 422.
- Enumerations are upper-case strings (see [1.6](#16-enumerations)).
- In a `PATCH`, an omitted field is left unchanged.
  `null` clears the nullable fields (`description` and `imageUrl` on an item).

### 1.3 Request limits and strictness

- A JSON body may be at most 64 KB, otherwise the response is 413 `PAYLOAD_TOO_LARGE`.
  An image upload may be at most 5 MiB.
- Malformed JSON is 400 `BAD_REQUEST`.
- Bodies and path parameters are strict.
  An unknown property is a 422 with `rule: "unrecognized_keys"` and `field: "(root)"`.
  This is deliberate, so a hopeful `"role": "ADMIN"` fails loudly instead of being ignored.
- The query string of `GET /orders` is strict in the same way.
  The query strings of the three report endpoints are not, and unknown parameters there are silently dropped.
- A `PATCH` must carry at least one recognised field, otherwise it is a 422 with `field: "(root)"` and `rule: "custom"`.
- Strings marked "trimmed" have surrounding whitespace removed before their length is checked, and the trimmed value is what is stored.
  Passwords are never trimmed.

### 1.4 Response headers

| Header | Where | Meaning |
|---|---|---|
| `X-Request-Id` | Every `/api/v1` response and the health probes, with one exception | Correlation id, identical to `requestId` in an error body and to the id on the server's log lines. An inbound `X-Request-Id` is reused only when it is at most 128 characters of `A-Z a-z 0-9 . _ -`. Anything else is replaced by a generated UUID. **Exception:** a request that the JSON body parser rejects (413 for a body over 64 KB, 400 for malformed JSON) is refused before an id is assigned, so it has no `X-Request-Id` header and its error body has `requestId: "unknown"`. `/metrics` is a separate server and sets none. |
| `Cache-Control: no-store` | Orders (create, list, detail, status, checkout, cancel), order payments (create, list), refunds, the KDS snapshot, the board and the three reports | Never cache these. |
| `Cache-Control: private, no-cache` | `GET /menu` | Store it, but revalidate with `If-None-Match` before reuse. |
| `ETag` | `GET /menu` | A weak validator, `W/"catalog-<n>"`. |
| `Retry-After` | 429 responses from the per-address rate limits | Seconds to wait. |
| `Idempotency-Replayed: true` | `POST /orders`, on a replay | The response is the stored original. |
| `Idempotent-Replay: true` | `POST /orders/:id/payments`, on a replay | The same signal under a different name (see [9](#9-differences-from-designmd-and-known-rough-edges)). |

`helmet`'s default security headers are set on every response, and `X-Powered-By` is removed.

## 2. Authentication and authorization

### 2.1 Credentials

Send `Authorization: Bearer <token>` on every route that is not public.
Two kinds of token arrive in the same header and are told apart by shape.
A token containing a `.` is a staff JWT, and anything else is a kiosk device token.

- A missing or malformed header, a token that fails verification, or an unknown device token is 401 `AUTH_TOKEN_INVALID`.
- Public routes never read the header at all, so a malformed `Authorization` header cannot break `POST /auth/login`.
- Public routes are `POST /auth/login`, `POST /auth/refresh`, `POST /devices/activate`, `GET /orders/board`, `POST /webhooks/stripe`, `GET /healthz` and `GET /readyz`.

### 2.2 Staff sessions

A staff member holds an access token and a refresh token.

| Token | Form | Lifetime | Setting |
|---|---|---|---|
| Access token | HS256 JWT with claims `sub` (user id), `role`, `type: "staff"`, `jti`, `iat`, `exp` | 900 seconds | `ACCESS_TOKEN_TTL_SECONDS` |
| Refresh token | Opaque 256-bit base64url string, stored only as a hash | 14 days | `REFRESH_TOKEN_TTL_SECONDS` |

The flow is:

1. `POST /auth/login` returns both tokens.
   Each login starts a new token family, so the till and the KDS screen are independent sessions.
2. Send the access token on every request.
   When it expires the API answers 401 `AUTH_TOKEN_EXPIRED`.
3. `POST /auth/refresh` with the refresh token returns a new pair and retires the old refresh token (rotation).
4. Presenting a refresh token that was already rotated is treated as theft.
   The whole family is revoked and the answer is 401 `AUTH_REFRESH_REUSED`.
   The client must sign in again.
5. `POST /auth/logout` revokes the family of the refresh token you send, and denies the access token you used.

Three things to know about the edges of a session:

- **Logout needs a live access token.** It requires both the `Authorization` header and a `refreshToken` in the body, so a client whose access token has expired must refresh before it can log out.
- **Role and active status are read at login and refresh, not on every request.**
  An access token that has already been issued keeps its role and is still accepted by REST routes until it expires, which is up to 15 minutes, even after the account is deactivated or demoted.
  New logins and refreshes for a deactivated account fail immediately.
  Open KDS sockets for that user are cut at once, on a best-effort basis (see [section 7](#7-realtime-socketio)).
- **Logout denies the access token for sockets only.**
  The denial list is consulted when a `/kds` socket connects, not by REST routes, so the access token you logged out with still works against REST until it expires.

### 2.3 Kiosk pairing and device tokens

A kiosk is a device, not a user.

1. An ADMIN or MANAGER calls `POST /devices`.
   The response carries a one-time `pairingCode` of 8 characters, valid for `PAIRING_CODE_TTL_SECONDS` (600 seconds).
2. The tablet calls `POST /devices/activate` with that code and receives a `deviceToken`.
   The token is shown once and is stored only as a hash.
3. The tablet sends `Authorization: Bearer <deviceToken>` on every request.

A device token is an ordinary database row, looked up on every request, so revoking it takes effect on the very next request.
`lastSeenAt` on the device is refreshed by requests at most once a minute, and by the realtime heartbeat for connected sockets.

| Device status | Meaning | Effect on the tablet |
|---|---|---|
| `PENDING` | Registered, not yet paired. | Has no token. |
| `ACTIVE` | Paired and ordering. | Normal. |
| `PAUSED` | Ordering paused by staff. | The token still works. `POST /orders` is refused with 409 `DEVICE_PAUSED`. Reading the menu, paying for or cancelling an existing own order, and sockets all continue, so the tablet can show an "ordering paused" screen. |
| `REVOKED` | Retired or stolen. | Every request is 401 `DEVICE_REVOKED`. Its open socket is cut. |

A kiosk is also scoped to its own orders.
Order reads, payments and cancellation are filtered to orders that this device placed.
An order that belongs to another device, or was placed by staff, answers 404, identical (apart from `requestId`) to the answer for an order that does not exist, so the response cannot be used to enumerate orders.

### 2.4 How a request is processed

Guards run in a fixed order, which decides which error you see first.

1. Request id and timing, security headers, then the JSON body parser (64 KB).
   Parser failures are 400 or 413.
2. **Authentication.** Skipped on public routes.
   Failures are 401.
3. **Rate limiting.** It runs after authentication so staff can be counted per user.
   Failures are 429, or 503 where a limit fails closed (see [4.1](#41-rate-limiting)).
4. **Roles.** Failures are 403 `FORBIDDEN_ROLE`, and `meta.requiredRoles` lists the roles the route accepts.
5. **Validation.** Failures are 422.
6. The handler.

Two consequences follow.
Hammering a route you are not allowed to call still spends your rate-limit budget, because the limiter runs before the role check.
A request rejected for a bad token never reaches the limiter, so volumetric defence against that case belongs at the edge.

Every route must declare either public access or a role list.
A route that declares neither fails closed with a 500, and `test/authz-matrix.e2e-spec.ts` fails if the application exposes a route that the matrix does not list.

### 2.5 Authentication errors

| Status | Code | When |
|---|---|---|
| 401 | `AUTH_TOKEN_INVALID` | Header missing or malformed. JWT signature wrong, wrong `type`, or unknown role. Device token unknown. Refresh token unknown. Logout with a refresh token that does not belong to the caller. |
| 401 | `AUTH_TOKEN_EXPIRED` | Access token past `exp` (refresh it). Also a refresh token past its 14 days. |
| 401 | `AUTH_REFRESH_REUSED` | A refresh token that was already rotated or revoked was presented. The family is now revoked. |
| 401 | `AUTH_INVALID_CREDENTIALS` | Wrong password, unknown email or deactivated account on login (the three are indistinguishable by design). Also `refresh` and `GET /auth/me` for an account that has since been deactivated. |
| 401 | `DEVICE_REVOKED` | A revoked device presented its token. |
| 403 | `FORBIDDEN_ROLE` | The principal's role is not allowed. `meta.requiredRoles` lists the accepted roles. A kiosk asking for a `CASH` payment gets the same code without `meta`. |

## 3. Errors

### 3.1 The envelope

Every non-2xx response from the API uses one shape, modelled on RFC 9457 and served as plain `application/json`.

```json
{
  "type": "https://cafepos.dev/errors/order-invalid-transition",
  "title": "Invalid order transition",
  "status": 409,
  "code": "ORDER_INVALID_TRANSITION",
  "detail": "Order is READY; cannot transition to IN_PREPARATION.",
  "requestId": "8f0c1d52-6a0e-4b9e-9d1c-3f4a5b6c7d8e",
  "errors": null,
  "meta": { "currentStatus": "READY", "requested": "IN_PREPARATION" }
}
```

| Field | Type | Meaning |
|---|---|---|
| `type` | string | `https://cafepos.dev/errors/` followed by the code in lower-case kebab form. It is an identifier, and nothing is guaranteed to be served there. |
| `title` | string | Short human-readable summary. |
| `status` | integer | The HTTP status, repeated. |
| `code` | string | A stable machine-readable code. **Switch on this, never on `detail`.** |
| `detail` | string | A human-readable explanation. Never contains secrets or stack traces. Messages from the framework are cut to 200 characters. |
| `requestId` | string | Matches the `X-Request-Id` header. Quote it when reporting a problem. It is `"unknown"` for the body-parser rejections described in [1.4](#14-response-headers). |
| `errors` | array or null | Field-level failures. Present only on validation 422s (see 3.3). |
| `meta` | object or null | Structured context for the specific code. The keys are listed in the catalog below. |

One exception: the 503 from `GET /readyz` is not an error envelope (see [6.13](#613-health-and-metrics)).

### 3.2 How framework errors map

Anything the framework or middleware rejects is mapped by status.

| Status | Code |
|---|---|
| 400 | `BAD_REQUEST` (malformed JSON, multipart errors other than size, any other 4xx without its own mapping) |
| 401 | `AUTH_TOKEN_INVALID` |
| 403 | `FORBIDDEN_ROLE` |
| 404 | `RESOURCE_NOT_FOUND` (also an unknown route, with `detail` such as `Cannot GET /api/v1/nothing`) |
| 409 | `CONFLICT` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 422 | `VALIDATION_FAILED` |
| 429 | `RATE_LIMITED` |
| 503 | `DEPENDENCY_UNAVAILABLE` |
| 5xx otherwise | `INTERNAL`, with `detail: "An unexpected error occurred."`. The cause is only in the server log. |

### 3.3 Validation errors

A body, query or path parameter that fails its schema is 422 `VALIDATION_FAILED` with an `errors` array.
All failures are reported together, not one at a time.

```json
{
  "type": "https://cafepos.dev/errors/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "code": "VALIDATION_FAILED",
  "detail": "One or more fields are invalid.",
  "requestId": "8f0c1d52-6a0e-4b9e-9d1c-3f4a5b6c7d8e",
  "errors": [
    { "field": "items.0.quantity", "rule": "too_big", "message": "Too big: expected number to be <=50" },
    { "field": "(root)", "rule": "unrecognized_keys", "message": "Unrecognized key: \"role\"" }
  ],
  "meta": null
}
```

- `field` is a dotted path, with array positions as plain numbers (`items.0.quantity`, not `items[0].quantity`).
  An issue about the object as a whole (an unknown key, an empty `PATCH`, a missing body) has `field: "(root)"`.
- `rule` is the Zod issue code, such as `invalid_type`, `invalid_format`, `invalid_value`, `too_small`, `too_big`, `unrecognized_keys` or `custom`.
  A few business-rule 422s use their own `rule` values instead (`principal` for a channel mismatch, `format` for a malformed cursor or idempotency key).
- `message` is human-readable and may change between releases.
- Some `VALIDATION_FAILED` responses carry no `errors` array.
  The report range check (`Unprocessable range`) is one, and it explains itself in `detail`.

| `PAYMENT_NOT_REFUNDABLE` | 409 | The payment is not `SUCCEEDED`, or its order is from an earlier business day. | - |
| `WEBHOOK_SIGNATURE_INVALID` | 400 | The Stripe signature is missing or matches none of the configured secrets. | - |

### 3.5 Reacting to errors

- **422** will not succeed unchanged.
  Fix the request, using `errors[]` to find the field.
- **409** is about state, not shape.
  `ORDER_INVALID_TRANSITION` carries `meta.currentStatus` precisely so a screen that lost a race can resync from the response instead of fetching again.
- **429** means wait `meta.retryAfterSeconds` before retrying.
  The `Retry-After` header carries the same number on the per-address limits.
- **503** `DEPENDENCY_UNAVAILABLE` is deliberate and retrying later works.
  A kiosk should show its offline screen and try again, and a till can fall back to cash.
- **5xx other than 503** is a bug on the server.
  Report the `requestId`.
- A network failure or timeout on `POST /orders` or `POST /orders/:id/payments` is safe to retry **if you sent an `Idempotency-Key`**, and not otherwise (see [4.2](#42-idempotency)).

## 4. Cross-cutting behaviour

### 4.1 Rate limiting

Limits are held in Redis, so they apply across all API instances.

| Rule | Applies to | Counted per | Limit | Block | If Redis is unreachable |
|---|---|---|---|---|---|
| `staffGeneral` | Every route without its own rule, including the public board and the webhook | Staff user id, else device id, else client address | 600 per minute | 1 minute | **Fails open.** The request is served uncounted, because this limit is a backstop and ordinary traffic is nowhere near it. |
| `login` | `POST /auth/login` | Client address | 20 per 15 minutes | 15 minutes | **Fails closed.** 503 `DEPENDENCY_UNAVAILABLE`, because here the limit is the brute-force defence. |
| `deviceActivation` | `POST /devices/activate` | Client address | 5 per hour | 1 hour | **Fails closed.** 503 `DEPENDENCY_UNAVAILABLE`. |
| `loginAccount` | `POST /auth/login` | Email address, case-insensitively | 5 failed attempts in a window of 15 minutes that starts at the first failure | Until the window ends | Login is refused by the `login` rule above. |

- The per-account lockout counts failures against the email that was asked for, even if no such account exists, so it does not reveal which emails are real.
  A locked account answers 429 even for the correct password.
  A successful login clears the count.
- A refusal is 429 `RATE_LIMITED` with `meta.retryAfterSeconds`.
  The per-address rules also send a `Retry-After` header.
  The per-account lockout sends **no** `Retry-After` header, so read `meta.retryAfterSeconds`.
- `GET /healthz` and `GET /readyz` are exempt.
- Staff already signed in keep working through a Redis outage, because access tokens are verified by signature and not against Redis.

### 4.2 Idempotency

`POST /orders` and `POST /orders/:id/payments` accept an `Idempotency-Key` header.
No other route does.
Send one whenever a client might retry, which for a kiosk on unreliable wifi is always.

**The key.**
It is optional, 8 to 128 characters of `A-Z a-z 0-9 . _ : -`, and surrounding whitespace is trimmed.
A malformed key is refused with 422 (`errors[0].field` is `"Idempotency-Key"`, `rule` is `"format"`) and is never silently ignored, because ignoring it would drop the protection the client believes it has.
A UUID is the intended value.

**What counts as the same request.**
The server stores a fingerprint with the key.
The fingerprint is a SHA-256 over the caller's identity and the parsed body with its keys sorted, so key order and omitted-versus-default fields do not matter.
For payments the order id is part of the fingerprint too.

| You send | Result |
|---|---|
| A new key | The request runs normally. |
| A known key with the same fingerprint | A **replay**: the stored response, with status `201`. |
| A known key with a different fingerprint | 409 `IDEMPOTENCY_CONFLICT`. |

**Important consequences.**

- Keys live in **one namespace shared by both endpoints**.
  Reusing an order's key for that order's payment is a different fingerprint, so it is a 409.
  Use a fresh key for each attempt on each endpoint.
- The fingerprint includes the caller, so one device cannot pull back another device's order by guessing a key.
- A replay is always `201`, never `200`, and its header is `Idempotency-Replayed: true` on orders but `Idempotent-Replay: true` on payments.
- A refused request stores nothing.
  A basket rejected because an item was briefly 86'd leaves the key free, so the same key can be retried the moment the item is back.
- Duplicates that arrive while the original is still running wait for it, and then replay.
  They do not create a second order.
- Payments are replayed before the order is re-checked.
  Retrying a cash payment that already moved the order to `PAID` returns the stored payment, not 409 `ORDER_NOT_PAYABLE`.
- The stored copy of a payment response has `clientAction: null`, because the client secret is a credential and is not written down.
  On a replay of a gateway payment that is still `PENDING`, the secret is fetched from Stripe again.
  **That replay can therefore fail with 503** if Stripe is unreachable.
- The key is also forwarded to Stripe as its idempotency key when the payment intent is created.
- Keys expire after 24 hours, and expired rows are deleted hourly.

### 4.3 Cursor pagination

Only `GET /orders` is paginated.
It returns `{ "orders": [...], "nextCursor": "..." }` and `nextCursor` is `null` on the last page.
Pass it back unchanged as `?cursor=`.

- The cursor is opaque.
  It happens to be base64url JSON holding the sort, the last row's sort value and its id, but do not parse it.
- A cursor is bound to the `sort` it was issued for.
  Using it with another `sort`, or editing it, is a 422 with `errors[0].field: "cursor"`, and the recovery is to request the first page again.
- A cursor does not encode your filters.
  Keep the filters identical on every page of one walk.
- Paging is by cursor rather than offset so that an order arriving mid-scroll does not shift later pages, and so that two orders sharing a timestamp are never dropped at a page boundary.
- Every other list is returned whole: staff, devices, categories, items, option groups and the menu.
  The KDS snapshot and the board are not paginated either, but each is capped at 200 entries, oldest first, and the cap truncates silently.

### 4.4 The menu cache

`GET /menu` is the one read a kiosk makes continually, so it is built for polling.

- The response carries `ETag: W/"catalog-<n>"` and `Cache-Control: private, no-cache`.
  A client that sends the same value back in `If-None-Match` gets `304` with no body.
  Comma-separated lists and `*` are honoured.
- `<n>` is a counter in Redis that is incremented after every successful non-`GET` request to the categories, items, option-groups and options routes.
  It is incremented before the write's own response is sent, so a client that re-polls immediately sees the change.
- If Redis is unreachable the menu is still served, built from Postgres, **without** an `ETag`, and a `304` is never returned.
  A client holding an `ETag` from before the outage therefore gets a fresh document instead of being pinned to a stale one.
- If the counter fails to increment while reads still work, kiosks can hold an out-of-date menu until the cached document expires, which is one hour.
- Kiosks are expected to poll about every 10 seconds.
- The menu is only for display.
  `POST /orders` always reads prices and availability from the database, so a stale menu can never cause an 86'd item to be sold.

### 4.5 CORS

CORS is off unless `CORS_ORIGINS` (comma-separated) is set, because native kiosk apps are not browsers and need no CORS.
When it is on:

| Setting | Value |
|---|---|
| Origins | The configured list |
| Methods | `GET`, `POST`, `PATCH`, `PUT`, `DELETE` |
| Request headers allowed | `Authorization`, `Content-Type`, `Idempotency-Key` |
| Response headers exposed | `X-Request-Id` only |
| Credentials | Not allowed |
| Preflight cache | 600 seconds |

### 4.6 The order lifecycle

Every move of an order goes through one guarded update, `UPDATE orders SET status = :to WHERE id = :id AND status = :from`.
Two clients racing on the same order cannot both win, and the loser gets 409 `ORDER_INVALID_TRANSITION` carrying the order's real current status.
Every move writes a row to the order's status history, naming the actor (`USER`, `DEVICE` or `SYSTEM`).

| From | To | Caused by |
|---|---|---|
| `DRAFT` | `PENDING_PAYMENT` | `POST /orders/:id/checkout` |
| `DRAFT` | `CANCELLED` | `POST /orders/:id/cancel` |
| `PENDING_PAYMENT` | `PAID` | A successful payment: the Stripe webhook, or a cash payment. **No endpoint sets `PAID` directly.** |
| `PENDING_PAYMENT` | `EXPIRED` | The expiry job, `ORDER_EXPIRY_SECONDS` (default 600) after creation or checkout |
| `PENDING_PAYMENT` | `CANCELLED` | `POST /orders/:id/cancel` |
| `PAID` | `IN_PREPARATION` | `POST /orders/:id/status` |
| `IN_PREPARATION` | `READY` | `POST /orders/:id/status` |
| `READY` | `COMPLETED` | `POST /orders/:id/status` |
| `PAID`, `IN_PREPARATION`, `READY`, `COMPLETED` | `REFUNDED` | The refund that takes the last of the captured amount (`POST /payments/:id/refunds`) |

- `CANCELLED`, `EXPIRED` and `REFUNDED` are terminal.
  `COMPLETED` can only go on to `REFUNDED`.
- A partial refund leaves the order where it is.
  `REFUNDED` means fully refunded.
- `expiresAt` is set while an order is `PENDING_PAYMENT` and is cleared the moment it leaves that status.
- Cancelling a paid order is not a cancel.
  It is a refund, and ends in `REFUNDED`, never `CANCELLED`.
- The status history is returned by `GET /orders/:id`.

### 4.7 Business day and queue numbers

- An order belongs to a **business day**, a `YYYY-MM-DD` date in `BUSINESS_TIMEZONE` (default `Asia/Bangkok`).
  The day rolls over at `BUSINESS_DAY_START_HOUR` (default 5, meaning 05:00 local), so an order taken at 00:30 carries the previous day's date and counts in that day's reports.
- Each order that enters `PENDING_PAYMENT` receives a **queue number** such as `A-042`, unique within its business day.
  It is three digits, zero-padded, and continues as `A-1000` on a very busy day instead of wrapping.
  Numbers are gapless, because the counter rolls back with a failed order.
- A `DRAFT` has `orderNumber: null` and `expiresAt: null`.
  The number and the expiry are claimed at checkout.
  A checked-out order keeps the business day it was parked on, even if the checkout happens after the rollover.
- Refunds are same-day only: the order's business day must equal the current one.

### 4.8 Background jobs

These run inside the API process and change state that the API then reports.
They are idempotent and safe to run on two instances at once.

| Job | Schedule | Effect |
|---|---|---|
| `expire-pending-orders` | Every minute | Moves overdue `PENDING_PAYMENT` orders to `EXPIRED` (actor `SYSTEM`). It cancels any live Stripe intent first, and leaves the order alone if Stripe says it was already paid. |
| `drain-payment-inbox` | Every 30 seconds | Applies stored webhook events that have not been processed yet. |
| `roll-up-yesterday` | 03:00 `Asia/Bangkok` | Finalizes the previous business day's sales rollup, which the reports read. |
| `reconcile-yesterday` | 03:00 `Asia/Bangkok` | Compares the gateway's captured total with the books. |
| `retention-nightly` | 04:00 `Asia/Bangkok` | Clears customer names on orders older than 90 days, trims webhook payloads older than 13 months, and deletes refresh tokens that expired or were revoked more than 30 days ago. |
| `retention-idempotency-keys` | Hourly, at minute 17 | Deletes expired idempotency keys. |
| `kiosk-presence` | Every minute | Stamps `lastSeenAt` for devices with a connected socket. |

Because of `retention-nightly`, `customerName` becomes `null` on orders older than 90 days.

### 6.1 Authentication

#### `POST /auth/login`

**Public** · **Success:** `200` `LoginResponse` · **Rate limit:** `login` per address, and the per-account lockout (see [4.1](#41-rate-limiting))

Exchanges an email and password for a token pair.
It returns 200 rather than 201, because a login creates nothing the client can address.

| Body field | Type | Required | Rules |
|---|---|---|---|
| `email` | string | yes | Trimmed, at most 254 characters, a valid email. Matched case-insensitively. |
| `password` | string | yes | 1 to 200 characters. There is no minimum length on login, so a failure never reveals which password policy was in force. |

- An unknown email, a wrong password and a deactivated account all produce the same 401.
  The server verifies a dummy hash when the email is unknown, so response time does not reveal which emails exist.
- Each login starts a new token family.

| Status | Code | When |
|---|---|---|
| 401 | `AUTH_INVALID_CREDENTIALS` | The credentials were not accepted. |
| 429 | `RATE_LIMITED` | Over 20 attempts per 15 minutes from this address (`Retry-After` is sent), or 5 failed attempts on this account in 15 minutes (`meta.retryAfterSeconds` only). |
| 503 | `DEPENDENCY_UNAVAILABLE` | Redis is unreachable. Login fails closed. |

Content-Type: application/json

{ "email": "manager@cafe.test", "password": "correct horse battery" }

#### `POST /auth/refresh`

**Public** · **Success:** `200` `TokenResponse` (no `user`) · **Rate limit:** `staffGeneral` per address

The refresh token is itself the credential, so no access token is needed, and clients call this exactly when theirs has expired.
The presented refresh token is retired and a new pair is issued in the same family.

| Body field | Type | Required | Rules |
|---|---|---|---|
| `refreshToken` | string | yes | 1 to 512 characters. |

| Status | Code | When |
|---|---|---|
| 401 | `AUTH_TOKEN_INVALID` | The token is unknown. |
| 401 | `AUTH_REFRESH_REUSED` | The token was already rotated or revoked. The whole family is revoked, including the child the legitimate client holds. Sign in again. |
| 401 | `AUTH_TOKEN_EXPIRED` | The refresh token is past its 14 days. It is retired. Sign in again. |
| 401 | `AUTH_INVALID_CREDENTIALS` | The account has been deactivated. |

#### `POST /auth/logout`

**Roles:** A M C B · **Success:** `204`, no body

Ends one session.
It revokes the token family that the supplied refresh token belongs to, and denies the access token used to make this call (for sockets, see [2.2](#22-staff-sessions)).
It affects only that session, so signing out at the till does not sign out the KDS.
It is safe to call twice.

| Body field | Type | Required | Rules |
|---|---|---|---|
| `refreshToken` | string | yes | 1 to 512 characters. Must belong to the caller. |

#### `POST /items/:id/image`

**Roles:** A M · **Success:** `200` `Item` with the new `imageUrl`

It returns 200 rather than 201, because the item already exists and is returned updated.

Send `multipart/form-data` with exactly one file part named `file`.

| Rule | Value |
|---|---|
| Size | At most 5 MiB. |
| Accepted formats | JPEG, PNG and WebP, **identified from the file's own bytes**. GIF and SVG are refused. |
| Declared `Content-Type` | May only reject. A declared type that is not JPEG, PNG or WebP is refused. `application/octet-stream` or an empty type is passed to the byte check. |
| Pixels | At most 40,000,000 decoded pixels. |

All metadata, including GPS coordinates, is dropped.
The result is stored under a content-addressed key `items/<sha256>.webp`, so the same picture uploaded twice occupies one object, and `imageUrl` is `<S3_PUBLIC_BASE_URL>/items/<sha256>.webp`.

| Status | Code | When |
|---|---|---|
| 404 | `RESOURCE_NOT_FOUND` | No such item. Checked before any decoding. |
| 413 | `PAYLOAD_TOO_LARGE` | The file is over 5 MiB. |
| 400 | `BAD_REQUEST` | Another multipart problem, such as a second file or a field with another name. |
| 415 | `IMAGE_TYPE_UNSUPPORTED` | The bytes are not an accepted format. `meta.accepted` lists `image/jpeg`, `image/png`, `image/webp`. |
| 422 | `IMAGE_FILE_MISSING` | There is no `file` part. |
| 422 | `IMAGE_UNPROCESSABLE` | The file is corrupt, truncated or over the pixel limit. |

### 6.8 Orders

#### `POST /orders`

**Roles:** A M C K · **Success:** `201` `OrderView` · **Idempotency:** `Idempotency-Key` header, optional (see [4.2](#42-idempotency))

Places an order.
One endpoint serves both channels, and the credential decides which: a device token places `KIOSK` orders and a staff token places `COUNTER` orders.
A barista cannot place orders.

| Body field | Type | Required | Rules |
|---|---|---|---|
| `channel` | `OrderChannel` | yes | Must match the credential: `KIOSK` for a device token, `COUNTER` for a staff token. A mismatch is a 422 with `errors[0].field: "channel"` and `rule: "principal"`. |
| `items` | array | yes | 1 to 30 lines. |
| `items[].menuItemId` | uuid | yes | |
| `items[].quantity` | integer | yes | 1 to 50. |
| `items[].optionIds` | uuid[] | no | At most 15. Default `[]`. A flat list of what the customer tapped. The server works out which group each belongs to. |
| `items[].notes` | string or null | no | Trimmed, at most 140 characters. Stored verbatim and never sanitised, so the renderer must escape it. |
| `customerName` | string or null | no | Trimmed, 1 to 40 characters. The only customer personal data the system holds. Cleared after 90 days. |
| `expectedTotalMinor` | integer | no | 0 to 10,000,000. The total the customer was shown. If it differs from the server's total the order is refused with `PRICE_MISMATCH`. A kiosk should always send it, so a customer is never charged a number they did not see. |
| `draft` | boolean | no | Counter only. `true` parks the basket as a `DRAFT` that holds no queue number (see `POST /orders/:id/checkout`). A kiosk sending `true` is a 422 with `errors[0].field: "draft"`. |

**Pricing.** Nothing the client says about money is believed, except that `expectedTotalMinor` can cause a refusal.

| Quantity | Rule |
|---|---|
| Line unit price | `max(0, basePriceMinor + sum of the selected options' priceDeltaMinor)` |
| Line total | `unitPriceMinor * quantity` |
| `subtotalMinor` and `totalMinor` | The sum of the line totals (equal in this version) |
| `vatMinor` | `round(totalMinor * VAT_BASIS_POINTS / (10000 + VAT_BASIS_POINTS))`. Prices are VAT-inclusive, so this is carved out of the total and is **not added**. The default is 700, which is 7%. |
| `currency` | The `CURRENCY` setting (default `THB`). |

Names and prices are copied onto the order, so later menu edits never change an order that already exists.

**What the order looks like.** An order that is not a draft is created `PENDING_PAYMENT`, with a queue number and `expiresAt` set `ORDER_EXPIRY_SECONDS` (default 600) from now.
A draft is created `DRAFT`, with `orderNumber: null` and `expiresAt: null`.

**Option rules.** They are checked per line against the groups attached to that item.
An option from any other group counts as unknown.
Every attached group must receive between its `minSelect` and `maxSelect` selections, and a group with `minSelect: 0` may receive none.
An item in an inactive category counts as unavailable.

**Order of checks.** Schema validation, then channel and draft rules, then the device pause, then option selections (422), then availability (409), then price (409).
A basket that is both stale-priced and contains an 86'd item therefore hears about the 86'd item first.
The whole thing runs in one transaction, and a refused order leaves nothing behind, not even its idempotency key.

| Status | Code | When |
|---|---|---|
| 409 | `DEVICE_PAUSED` | The kiosk's device is paused. |
| 409 | `ORDER_ITEM_UNAVAILABLE` | An item or option is 86'd, an item id is unknown, or an item is in an inactive category. `meta.itemIds` and `meta.optionIds` list every offender so the screen can highlight them. |
| 409 | `PRICE_MISMATCH` | `expectedTotalMinor` differs from the server's total. `meta` holds both numbers. |
| 409 | `IDEMPOTENCY_CONFLICT` | The key was already used for a different request. |
| 422 | `OPTION_SELECTION_INVALID` | See below. |
| 422 | `VALIDATION_FAILED` | A schema failure, a channel mismatch, a kiosk `draft`, or a malformed `Idempotency-Key`. |

`meta.violations` on `OPTION_SELECTION_INVALID` lists every problem in the whole basket at once.

| Violation field | Present for | Meaning |
|---|---|---|
| `itemIndex` | all | Position in the submitted `items` array. |
| `rule` | all | `UNKNOWN_OPTION`, `DUPLICATE_OPTION`, `MIN_SELECT` or `MAX_SELECT`. |
| `optionIds` | `UNKNOWN_OPTION`, `DUPLICATE_OPTION` | The offending option ids. |
| `optionGroupId`, `optionGroupName` | `MIN_SELECT`, `MAX_SELECT` | The group whose bounds were broken. |
| `selected` | `MIN_SELECT`, `MAX_SELECT` | How many options were selected from that group. |
| `allowed` | `MIN_SELECT`, `MAX_SELECT` | `{ "minSelect": n, "maxSelect": n }`. |

A line with an unknown or duplicate option is not also checked against group bounds, because its intended selection is not known.

| Status | Code | When |
|---|---|---|
| 404 | `RESOURCE_NOT_FOUND` | No such order. For a kiosk, also an order placed by another device or by staff. The two answers are identical, apart from `requestId`, on purpose. |

#### `POST /orders/:id/status`

**Roles:** A M C B · **Success:** `200` `OrderSummary`

The kitchen advancing a ticket.
It exposes only three moves, and nothing here can mark an order paid.

| From | `to` |
|---|---|
| `PAID` | `IN_PREPARATION` |
| `IN_PREPARATION` | `READY` |
| `READY` | `COMPLETED` |

| Body field | Type | Required | Rules |
|---|---|---|---|
| `to` | `OrderStatus` | yes | Any status value is accepted by the schema. Whether the move is allowed is decided afterwards. |

- Asking for a real status that this route does not allow is a 409 about the transition, not a 422 about the field.
- The 409 carries the order's actual `currentStatus`, so a screen that lost a race can resync from the response.
- A move to `READY` publishes `order.ready`, and every other move publishes `order.updated` (see [section 7](#7-realtime-socketio)).

| Status | Code | When |
|---|---|---|
| 404 | `RESOURCE_NOT_FOUND` | No such order. |
| 409 | `ORDER_INVALID_TRANSITION` | The move is not one of the three above, or another screen moved the order first. `meta` holds `currentStatus` and `requested`. |

#### `POST /orders/:id/checkout`

**Roles:** A M C · **Success:** `200` `OrderSummary`

Sends a parked counter order to the queue (`DRAFT` to `PENDING_PAYMENT`).
No body is needed.

- The queue number and the payment window (`expiresAt`) are claimed in the same transaction as the status change.
- It does **not** re-price, so the total the cashier already read out stays the total.
- The order keeps the business day it was parked on.
- Nothing is published to realtime clients, because a `PENDING_PAYMENT` order is on no board.

| Status | Code | When |
|---|---|---|
| 404 | `RESOURCE_NOT_FOUND` | No such order. |
| 409 | `ORDER_INVALID_TRANSITION` | The order is not a `DRAFT`. `meta.requested` is `PENDING_PAYMENT`. |

#### `POST /orders/:id/cancel`

**Roles:** A M C K (own) · **Success:** `200` `OrderSummary`

Calls off an order before it has been paid.
A kiosk may cancel its own order, and a barista may not cancel at all.

| Body field | Type | Required | Rules |
|---|---|---|---|
| `reason` | string or null | no | Trimmed, 1 to 200 characters. Recorded on the history row. Send `{}` when there is no reason. |

- Only `DRAFT` and `PENDING_PAYMENT` orders can be cancelled.
- If the order has a live Stripe payment, the server cancels the payment intent **first**, then cancels the order and marks that payment `CANCELLED`.
  This stops a customer confirming a QR code for an order that no longer exists.
- Cancelling a paid order is a refund (`POST /payments/:id/refunds`), not a cancel.
- Publishes `order.updated`.

| Status | Code | When |
|---|---|---|
| 404 | `RESOURCE_NOT_FOUND` | No such order, or for a kiosk, not its own. |
| 409 | `ORDER_INVALID_TRANSITION` | The order is in any other status. `meta.requested` is `CANCELLED`. |
| 409 | `ORDER_ALREADY_PAID` | The customer paid while the cancel was in flight. Nothing is cancelled and the order will become `PAID` shortly. A kiosk should show the order number, not an error. |
| 503 | `DEPENDENCY_UNAVAILABLE` | Stripe could not be reached to cancel the intent. The cancel is refused and the order is untouched. Retry shortly, or let the order expire. |

### 6.10 Payments and refunds

#### `POST /orders/:id/payments`

**Roles:** A M C K (own) · **Success:** `201` `PaymentView` · **Idempotency:** `Idempotency-Key` header, optional (see [4.2](#42-idempotency))

Opens a payment against an order.
The response is `no-store`, because it can carry a client secret.

| Body field | Type | Required | Rules |
|---|---|---|---|
| `method` | `PaymentMethod` | yes | `CARD`, `PROMPTPAY` or `CASH`. |
| `cashTenderedMinor` | integer | for `CASH` only | A positive integer. Required for `CASH` and rejected for anything else. |

Checks run in this order: a stored replay of the key, the order exists and is visible to the caller, it has not expired, it is `PENDING_PAYMENT`, it has no live payment, and then the cash rules.

**`CASH`** is counter-only and settles immediately.
The payment is created `SUCCEEDED` and the order moves to `PAID` in the same transaction, and `order.paid` is published.
`amountMinor` is the order total, not the amount handed over, so work out change as `cashTenderedMinor - amountMinor`.
`cashTenderedMinor` must be at least the total.

**`CARD` and `PROMPTPAY`** open a Stripe PaymentIntent.
The two behave identically and the `method` you send is not stored or honoured as a choice of rail.
The intent uses Stripe's dynamic payment methods, so the customer picks the rail inside Stripe's Payment Element after the intent exists, and which rails appear is a Stripe Dashboard setting.
The response has `status: "PENDING"`, `method: null` (the webhook fills it in later) and `clientAction.clientSecret`, which the client hands to the Payment Element.
No card data ever touches this API.

After creating a gateway payment, a kiosk should wait for `payment.succeeded` on the `/kiosk` socket, or poll `GET /orders/:id` as a fallback.
It must not decide success itself, and for PromptPay it must take the QR code down the instant `payment.succeeded` arrives.

There is no endpoint that cancels a payment on its own.
A live payment ends when the customer pays, when a failure or cancellation webhook arrives, when the order is cancelled, or when the order expires.
A client that receives `PAYMENT_ALREADY_ACTIVE` should continue with the payment that exists, whose id is in `meta.activePaymentId`.

| Status | Code | When |
|---|---|---|
| 403 | `FORBIDDEN_ROLE` | A kiosk asked for `CASH`. This is raised inside the handler, so `meta.requiredRoles` is absent. |
| 404 | `RESOURCE_NOT_FOUND` | No such order, or for a kiosk, not its own. |
| 409 | `ORDER_EXPIRED` | The order has expired. Order again. |
| 409 | `ORDER_NOT_PAYABLE` | The order is not `PENDING_PAYMENT` (a `DRAFT`, or already `PAID` or beyond). `meta.currentStatus` says which. |
| 409 | `PAYMENT_ALREADY_ACTIVE` | The order already has a `PENDING` or `PROCESSING` payment. Two tills racing are settled by a database constraint and get the same answer. |
| 409 | `IDEMPOTENCY_CONFLICT` | The key was already used for a different request, including a request on another order or the order-creation endpoint. |
| 422 | `CASH_TENDER_INSUFFICIENT` | The tender is below the total. `meta` holds `tenderedMinor` and `requiredMinor`. |
| 422 | `VALIDATION_FAILED` | `CASH` without a tender, or a tender on a non-cash method (`errors[0].field` is `cashTenderedMinor`). |
| 503 | `DEPENDENCY_UNAVAILABLE` | Stripe could not be reached, or a replay could not re-fetch the client secret. A till can fall back to cash. |

```json
{
  "id": "0197f3b1-7a2d-7e3f-8a41-5b6c7d8e9f01",
  "status": "PENDING",
  "method": null,
  "amountMinor": 17500,
  "currency": "THB",
  "provider": "STRIPE",
  "clientAction": { "type": "CONFIRM_WITH_CLIENT_SECRET", "clientSecret": "pi_3Abc..._secret_..." }
}
```

#### `GET /orders/:id/payments`

**Roles:** A M C B K (own) · **Success:** `200` `PaymentAttemptView[]`

Every payment attempt against an order, oldest first, including failed ones.
A barista may read this to see why an order is not paid, but cannot open a payment.
The client secret is never returned here.

| Status | Code | When |
|---|---|---|
| 404 | `RESOURCE_NOT_FOUND` | No such order, or for a kiosk, not its own. |

#### `POST /payments/:id/refunds`

**Roles:** A M · **Success:** `201` `RefundView`

Records a full or partial refund.
`:id` is a **payment** id, which you can read from `GET /orders/:id/payments`.

**This is bookkeeping only.**
No money moves through Stripe, and the API has no gateway refund call.
Staff settle from the till, and this route records that they did.

| Body field | Type | Required | Rules |
|---|---|---|---|
| `amountMinor` | integer | yes | Positive, and at most what is still unrefunded on the payment. |
| `reason` | string | yes | Trimmed, 1 to 200 characters. Required, unlike a cancellation's. |

- The payment must be `SUCCEEDED`.
- The order must belong to the **current** business day.
  Refunds against an earlier day are refused, because a till reconciled at close cannot be reopened.
- The payment row is locked while the remaining amount is computed, so two managers cannot both over-refund it.
- A partial refund leaves the order where it is.
  The refund that takes the last of the captured amount sets `fullyRefunded: true`, moves the order to `REFUNDED`, and publishes `order.updated`.
- This route takes **no** `Idempotency-Key`.
  Sending the same request twice records two refunds, limited only by the amount remaining.

| Status | Code | When |
|---|---|---|
| 404 | `RESOURCE_NOT_FOUND` | No such payment. |
| 409 | `PAYMENT_NOT_REFUNDABLE` | The payment is not `SUCCEEDED`, or its order is from an earlier business day. `detail` says which. |
| 422 | `REFUND_EXCEEDS_REMAINING` | The amount is more than what is left. `meta` holds `requestedMinor` and `remainingMinor`. |

### 6.11 Stripe webhook

#### `POST /webhooks/stripe`

**Public (authenticated by signature)** · **Success:** `200` `{ "received": true }` · **Rate limit:** `staffGeneral` per address

Stripe's callback into the system.
This route is for Stripe, not for application clients.

| Request header | Required | Meaning |
|---|---|---|
| `Stripe-Signature` | yes | Stripe's signature over the exact raw body. |

The body is the event JSON exactly as Stripe sent it.
Do not re-serialise it, because the signature covers the original bytes.

- The signature is checked against every secret in `STRIPE_WEBHOOK_SECRETS`, newest first, which is what allows a secret to be rotated with both accepted for a while.
  The body is not interpreted until a signature matches.
- The event is **stored first**, deduplicated by Stripe's event id, and only then acknowledged.
  Processing continues after the response, and the 30-second inbox sweep is the backstop.
  A redelivery of an event that is already stored is acknowledged with 200 and not processed again.
- Stripe should be configured to send `payment_intent.succeeded`, `payment_intent.payment_failed` and `payment_intent.canceled`, and the server's Stripe client is pinned to API version `2026-08-26.dahlia`.
- Create the webhook endpoint on that same API version.
  The Stripe Dashboard creates new endpoints on the account's latest version, which can be newer than the pin, so create staging and production endpoints through Stripe's API or CLI with `api_version` set to `2026-08-26.dahlia`.
  Stripe's webhook versioning documentation is the authority on this.

| Event type | Effect |
|---|---|
| `payment_intent.succeeded` | If the amount and currency match the payment and the order is `PENDING_PAYMENT`, the payment becomes `SUCCEEDED`, its method is resolved from Stripe, the order becomes `PAID` (actor `SYSTEM`), and `order.paid` and `payment.succeeded` are published. |
| `payment_intent.payment_failed` | The payment becomes `FAILED` unless it already succeeded, and `payment.failed` is published. |
| `payment_intent.canceled` | The payment becomes `CANCELLED`. |
| Anything else | Stored and acknowledged, nothing done. |

An event the system refuses to act on (an amount or currency mismatch, an unknown intent, a success for an order that is not `PENDING_PAYMENT`, a failure for a payment that already succeeded) stays unprocessed in the inbox and is logged at `error`.
It also appears in `unmatchedEvents` of the Z-report reconciliation.

| Status | Code | When |
|---|---|---|
| 400 | `WEBHOOK_SIGNATURE_INVALID` | The header is missing, or no configured secret verifies the body. The response never says which. |
| 500 | `INTERNAL` | The event could not be stored, so Stripe will redeliver it. Also returned if the application was started without raw-body capture, which is a deployment fault. |

### 6.12 Reports

All three reports are for ADMIN and MANAGER, and are `no-store`.

- Dates are business days, `YYYY-MM-DD`, and must be real calendar dates.
- `to` (or `businessDay`) must not be after the current business day, otherwise the answer is 422 `VALIDATION_FAILED` with the title `Unprocessable range` and no `errors` array.
- `provisional: true` means the range includes the business day that is still trading, so its figures can still change.
- A day is read from its finalized nightly rollup when one exists, and is otherwise computed live from orders.
  If more than 31 days of a `groupBy=day` sales range, or of a top-items range, have no rollup, the answer is 503 `DEPENDENCY_UNAVAILABLE`, which means the nightly rollup has not been running.
- Revenue is the sum of `SUCCEEDED` payments, and an order is "settled" when it has one.
  Revenue is **gross**: refunds are reported separately and are not subtracted from sales buckets or top items.
- Unknown query parameters are ignored.

#### `GET /reports/sales`

**Roles:** A M · **Success:** `200` `SalesReport`

| Query parameter | Type | Required | Rules |
|---|---|---|---|
| `from` | `YYYY-MM-DD` | yes | Not after `to`. |
| `to` | `YYYY-MM-DD` | yes | Not after the current business day. |
| `groupBy` | `day` or `hour` | no | Default `day`. |

The range is at most 366 days for `day`, and at most 31 days for `hour`, counting both ends.

- `day` returns one bucket per business day in the range, including days with no sales (zero revenue, `avgTicketMinor: null`).
- `hour` returns only hours that had sales, labelled `<business day>T<HH>`, where `HH` is the local wall-clock hour in `BUSINESS_TIMEZONE`.
  The date part is the **business** day, so an order at 00:30 under a 05:00 rollover is labelled with the previous date.
  Hourly buckets are always computed live.

#### `GET /reports/top-items`

**Roles:** A M · **Success:** `200` `TopItemsReport`

| Query parameter | Type | Required | Rules |
|---|---|---|---|
| `from` | `YYYY-MM-DD` | yes | Not after `to`. |
| `to` | `YYYY-MM-DD` | yes | Not after the current business day. The range is at most 366 days. |
| `limit` | integer | no | 1 to 50. Default 10. |

Items are ranked by `quantity` descending, then by `name`.
Quantities are summed across the range by `menuItemId`, so an item renamed during the range is one entry, shown under its most recent name.
Only items on orders that took money are counted.

#### `GET /reports/z-report`

**Roles:** A M · **Success:** `200` `ZReport`

The end-of-day report.

| Query parameter | Type | Required | Rules |
|---|---|---|---|
| `businessDay` | `YYYY-MM-DD` | yes | Not after the current business day. |

| Field | Meaning |
|---|---|
| `orders` | How many of the day's orders ended in each of `completed`, `refunded`, `cancelled` and `expired`. Counted whether or not money was taken. |
| `revenueMinor.total` | The sum of the day's `SUCCEEDED` payments. |
| `revenueMinor.byMethod` | The same money by `CARD`, `PROMPTPAY` and `CASH`, plus `UNKNOWN` for a gateway payment whose rail could not be resolved. The parts always add up to `total`. |
| `refundsMinor` | The sum of the day's `SUCCEEDED` refunds. |
| `vatMinor` | The VAT carved out of the orders that took money. |
| `reconciliation` | Stripe against the books for the day, covering Stripe payments only. Cash is excluded. See `ReconciliationReport` in 5.6. |
| `reconciliationUnavailable` | Non-null exactly when `reconciliation` is null, and says why. |

`reconciliationUnavailable` has three values, and they are never merged because they page different people.

| Value | Meaning |
|---|---|
| `DAY_STILL_TRADING` | The day is the current business day, so a comparison would only measure work in progress. |
| `GATEWAY_UNREACHABLE` | Stripe could not be reached, or did not answer within 5 seconds. |
| `DATABASE_UNAVAILABLE` | Stripe answered, but this system failed while narrowing the unmatched events to the day. |

Every figure outside `reconciliation` is computed without the gateway, so the report is always served, with the reconciliation block left out when it cannot be trusted.

```json

  "provisional": false,
  "orders": { "completed": 412, "refunded": 3, "cancelled": 9, "expired": 17 },
  "revenueMinor": { "total": 4812000, "byMethod": { "CARD": 2100000, "PROMPTPAY": 2300000, "CASH": 412000 } },
  "refundsMinor": 21500,
  "vatMinor": 314897,
  "reconciliation": {
    "businessDay": "2026-06-11",
    "gatewayCapturedMinor": 4400000,
    "dbRecordedMinor": 4400000,
    "deltaMinor": 0,
    "unmatchedEvents": [],
    "notCaptured": []
  },
  "reconciliationUnavailable": null
}
```

## 7. Realtime (Socket.IO)

Realtime is push for screens that would otherwise poll.
It is best effort, and the REST snapshot endpoints are always the way to recover.

### 7.1 Connecting

Use a Socket.IO v4 client against the API origin, on the default path `/socket.io`, with the namespace in the URL.
There are three namespaces, because the three audiences authenticate differently and each needs its own gate.

| Namespace | Audience | Credential | Rooms |
|---|---|---|---|
| `/kds` | Staff screens | A staff access token (any role) | None for routing. Rooms exist only so a revocation is one operation. |
| `/kiosk` | Kiosk tablets | A device token | One room per device, so a tablet hears only about its own orders. |
| `/board` | Public queue board | None | None |

Send the credential as `auth: { token }` in the handshake.
An `Authorization: Bearer <token>` header is accepted too, for clients that are not browsers.

```js
import { io } from "socket.io-client";

const kds = io("https://api.example.com/kds", { auth: { token: accessToken } });

kds.on("connect_error", (err) => {
  // err.message is always "unauthorized". Refresh the access token or sign in again.
});
kds.on("order.paid", (ticket) => upsert(ticket));
kds.on("order.updated", (ticket) => upsert(ticket));
kds.on("order.ready", (ticket) => upsert(ticket));
kds.io.on("reconnect", () => reloadSnapshot()); // GET /api/v1/kds/orders
```

- Authentication happens **once, at the handshake**, as middleware.
  A rejected client receives `connect_error` and never a `connect`.
- Every failure is the same message, `unauthorized`: missing, malformed, expired, forged and revoked tokens all look identical, so a socket cannot be used as an oracle.
- On `/kds` the handshake also checks a short-lived Redis denial list, and **fails closed** if Redis is unreachable.
  A refused KDS screen can still poll `GET /kds/orders`.
- A kiosk's device token is checked against the database at the handshake, so a revoked or unpaired device is refused there.
  A paused device connects normally.
- The handshake of a kiosk also refreshes `lastSeenAt`.

### 7.2 Cutting a live connection

Because a socket authenticates once, sockets are cut when the credential is withdrawn.

| Action | Sockets cut |
|---|---|
| `PATCH /users/:id` changing `role` or `isActive` | Every `/kds` socket for that user |
| `POST /auth/logout` | The `/kds` sockets that used the access token being logged out |
| `POST /devices/:id/revoke` | The `/kiosk` sockets for that device |

The cut travels over Redis pub/sub to whichever instance holds the socket.
It is best effort, and a failure is logged at `error`.
A cut client reconnects and is then refused at the handshake.

### 7.3 Events

Every payload except the board's is a `KdsTicket`, which is the order and its lines, read from the database **after** the transaction that caused the event has committed.
Events are full snapshots, never diffs, so a client can always render from the latest one.

| Namespace | Event | Payload | Sent when |
|---|---|---|---|
| `/kds` | `order.paid` | `KdsTicket` | An order becomes `PAID`, by a Stripe success or a cash payment. |
| `/kds` | `order.updated` | `KdsTicket` | An order moves to `IN_PREPARATION` or `COMPLETED` through `POST /orders/:id/status`, is cancelled, or is fully refunded. |
| `/kds` | `order.ready` | `KdsTicket` | An order moves to `READY`. |
| `/kiosk` | `payment.succeeded` | `KdsTicket` of the order | The Stripe webhook marks the payment succeeded. Sent to the device that placed the order. |
| `/kiosk` | `payment.failed` | `KdsTicket` of the order | A failure webhook that actually changed the payment. Sent to the device that placed the order. |
| `/kiosk` | `order.ready` | `KdsTicket` | The order moves to `READY`. Sent to the device that placed it. |
| `/board` | `board.updated` | `BoardEntry[]`, the **whole** list | A batch of events that included `order.updated` or `order.ready`. |

Points that catch integrators out:

- **A payload can describe an order that has left the board.**
  An `order.updated` after a cancellation or a refund carries `status: "CANCELLED"` or `"REFUNDED"`.
  A KDS must drop any ticket whose status is not `PAID`, `IN_PREPARATION` or `READY`.
- **The `payment.*` payload is the order's ticket, not a payment object.**
  It has no payment id.
  Read `GET /orders/:id/payments` if you need one.
- **A kiosk only ever hears about orders it placed.**
  An order placed at the counter has no device and reaches no kiosk.
- **The board gets the entire list each time**, so a client that reconnects mid-rush renders correctly from the next event.

### 7.4 What is not announced

| Not announced | Consequence |
|---|---|
| Order creation, checkout, payment creation, and a `payment_intent.canceled` webhook | None for screens, because a `PENDING_PAYMENT` order is on no board. |
| The expiry job moving an order to `EXPIRED` | A kiosk is not told that its unpaid order expired. It finds out on its next call, which is a 409 `ORDER_EXPIRED` from `POST /orders/:id/payments`. |
| `order.updated` to a kiosk | A kiosk is **never** sent `order.updated`. It is not told when its order is `COMPLETED`, `REFUNDED`, or cancelled by staff. It must poll `GET /orders/:id`. |
| A second event when an order becomes `READY` | `READY` publishes only `order.ready`, not `order.updated` as well. A KDS that listens only for `order.updated` misses it. |

### 7.5 Delivery and recovery

- Publishing is deliberately outside the transaction.
  A push lost to a Redis blip costs a screen one refresh and never leaves it holding a state the database does not have.
- Events are clustered across API instances with the Redis adapter, so it does not matter which instance a screen is connected to.
- Recovery is always the same: call the snapshot endpoint.

| Audience | Recovery call |
|---|---|
| `/kds` | `GET /kds/orders` |
| `/board` | `GET /orders/board` |
| `/kiosk` | `GET /orders/:id` for the order in hand |

- Socket.IO uses the same CORS origins as the REST API (`CORS_ORIGINS`), with credentials allowed.

These use `curl`.
Set `BASE=http://localhost:3000/api/v1`, and use a fresh UUID for every `Idempotency-Key`.

**Sign in, and use the token.**

```bash
curl -s -X POST $BASE/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"<email>","password":"<password>"}'
# keep accessToken and refreshToken, then:
curl -s $BASE/auth/me -H "Authorization: Bearer $ACCESS"
```

## 9. Differences from DESIGN.md and known rough edges

### 9.1 Where the code differs from DESIGN.md

`DESIGN.md` has been reconciled with the code in most places.
These are the differences that remain.

| Topic | DESIGN.md | The code |
|---|---|---|
| Replay header | §5.7 names `Idempotency-Replayed: true` for any replay. | `POST /orders` sends that. `POST /orders/:id/payments` sends `Idempotent-Replay: true`. This looks unintentional. |
| Replay status | §5.7: the stored response, "200/201". | Always `201`. |
| Error code catalog | §9.2 lists the codes. | The code also raises `BAD_REQUEST`, `CONFLICT`, `USER_EMAIL_EXISTS`, `USER_LAST_ADMIN`, `CATEGORY_NAME_EXISTS`, `CATEGORY_UNKNOWN`, `OPTION_GROUP_MINMAX_INVALID`, `OPTION_GROUP_UNKNOWN`, `IMAGE_FILE_MISSING`, `IMAGE_TYPE_UNSUPPORTED` and `IMAGE_UNPROCESSABLE`, which §9.2's table omits (some appear in the §5.2 endpoint tables). |
| `errors[].field` format | §9.1 example: `items[0].quantity`. | `items.0.quantity`. |
| `requestId` format | §9.1 example: `req_8f3ka92`. | A UUID, or a safe inbound `X-Request-Id`. |
| `Retry-After` on lockout | §10.2 asks for the header. | The per-address limits send it. The per-account lockout sends only `meta.retryAfterSeconds`. |
| Webhook failure policy | §9.3: "on processing failure return 5xx so Stripe retries". | The event is stored and acknowledged with 200 first, then processed. The 30-second inbox sweep recovers failures. 5xx is returned only when the event cannot be stored. |

### 9.2 Known rough edges

None of these is a crash.
Each is behaviour an integrator is likely to trip over, stated plainly so it can be designed around or fixed.

**Idempotency**

- The two replay headers have different names, so a client handling both endpoints must check `Idempotency-Replayed` and `Idempotent-Replay`, or compare bodies instead.
- Keys share one namespace across orders and payments, so reusing an order's key for its payment is a 409.
- Replaying a pending gateway payment re-fetches the client secret from Stripe, so the replay can be a 503.
- `POST /payments/:id/refunds` takes no `Idempotency-Key`, and a retried request records a second refund.

**Authentication and limits**

- Deactivating or demoting a staff member does not stop REST calls made with an access token already issued, for up to `ACCESS_TOKEN_TTL_SECONDS` (15 minutes).
  Logout has the same limit, because the denial list is only consulted by `/kds` sockets.
- The per-account login lockout returns no `Retry-After` header.
  Browser clients on another origin cannot read `Retry-After`, `ETag` or either replay header, because CORS exposes only `X-Request-Id`.
- The per-address limits (`login`, `deviceActivation`, and `staffGeneral` on public routes) key on Express's `req.ip`.
  Nothing in the repository sets Express's `trust proxy`.
  Behind a load balancer `req.ip` would then be the balancer's address unless the platform preserves the client address, and every client would share one budget.
  This has not been checked against a real deployment, and is worth confirming before launch.

**Realtime**

- The silent paths in [7.4](#74-what-is-not-announced): a kiosk never receives `order.updated`, expiry is not announced, and `READY` has no companion `order.updated`.
- The KDS snapshot and the board are capped at 200 entries, oldest first, and truncate without any signal.

**Smaller things**

- `DEVICE_PAUSED` is enforced only by `POST /orders`.
  A paused kiosk can still open a payment for, or cancel, an order it already placed.
- A request with no body is a 422, even where every field is optional (`POST /orders/:id/cancel`).
- `GET /orders?q=` matches an order number exactly and case-sensitively, so `a-042` finds nothing.
- A request the JSON body parser rejects (413 for a body over 64 KB, 400 for malformed JSON) has no `X-Request-Id` header and `requestId: "unknown"`, so it cannot be correlated with a log line.
- The 503 bodies from `/readyz` are not the error envelope.
- `OrderStatusChange` omits the `reason` that is stored with a cancellation or refund.
- `PaymentStatus` defines `PROCESSING` and `EXPIRED`, and `RefundStatus` defines `PENDING` and `FAILED`, but the code does not currently produce them.
